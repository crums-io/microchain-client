# microchain-client

Client-side tooling for committing rows from an on-prem SQL database to a
remote [SkipLedger](https://github.com/crums-io/skipledger) microchain hosted by a
service implementing this [API](./microchain-api/README.md).

## What it does, how it works

A microchain records tamper-evident history (64 bytes per row) of an SQL table (or view) that
*behaves* like a ledger. Besides an immutable audit trail, a microchain allows its owner
to provide succinct proofs of individual entries in the ledger.

To be ledger-like the SQL views you declare and track **MUST** meet the following requirements:

1. You can retrieve any ledger row using only its "row number". This "row number"
is a 1-based ascending number matching the order that rows are added (appended) to
the [logical] ledger. You can use a table's primary (numeric) key (or any other sequence) as
a *surrogate* for the ledger's row number; if there are gaps with such "row numbers",
the missing rows are treated as *NULL* rows.

2. Once a ledger's first *N* rows are committed to its chain, none of their
column-values should ever change. (Changing any value, invalidates the row's hash in
the commitment chain, see below.)

### Commitment workflow

Rather than send raw row-data to the chain server, clients compute the SHA-256 hash
of each row locally and submit only those hashes. The website's new-chain form defaults
to salting every column, so no information leaks unless the chain owner opts out; whether
a chain is salted is fixed once rows start being committed (see `salted` below).
The server appends these
*input* hashes to a SkipLedger, a compact hash-pointer data structure that records
both the input- and the computed commitment-hash per row (64-byte block per row). Owing to
the linked structure of the hash computation, the hash of each row already bakes in
the cumulative content of every row before it. So row *N*'s commitment-hash also functions as the state of the
entire ledger when it had exactly *N* rows. This in turn allows the ledger owner to generate
tamper evident, succinct "receipts" linking the content of any row to the current commitment hash of
the ledger (see next).

### Tamper-evident receipts

Ledger owners can generate and issue structured, verifiable, tamper-evident receipts detailing
the contents of one or more rows, in one or more microchains. They are called receipts because
conventional receipts are usually recorded in (their data comes from) one or more ledgers.

#### Downstream redactable

Receipts are typically *semi*-private information; they are shared with counterparties
(e.g. customers) or other interested parties. Given a receipt, a party may want to share information
in the receipt with other downstream parties, but perhaps with parts redacted. Individual values
in the receipts generated by this library are *independently* redactable. They have this
*shred-with-glue* property: the remaining revealed parts of a receipt are still verifiable.

## Configuration

Each chain lives under a URL endpoint, usually of the form
`<org-URL>/<chain>`. The following REST endpoints about the chain are *public*:

1. `<org-URL>/<chain>/info` - Declares which column values are salted/not-salted (fixed thru
the life of a microchain), as well as any optional meta information (title, description, etc.) about the chain.
2. `<org-URL>/<chain>/state` - Returns cryptographic data about the state of the chain. Links the
hashes of any subset of rows in a succinct proof and underlies how receipts are verified. 

Excepting these (`/info` and `/state`), access to the chain's other REST endpoints is protected
by bearer token. These concern the chain's configuration data, and importantly, the `/commit`
REST endpoint (used to commit new rows).

### Where configuration data live

A chain's configuration data may live at the server, at the client, or both.
The decision "where a piece of configuration data lives" is often a tradeoff of convenience and security.
Some configuration data is *sensitive*: for example, a chain's *salt-seed* (used to protect
against guessing a row's values from the row's hash) must be kept *secret*, but also, must not be lost (!).

Chain configuration settings can be sourced from 3 levels, each overriding the previous:

1. Retrieved from the server (the chain's `/salts` and `/sql-config` endpoints).
2. From a local config file.
3. From the command-line.  (*Avoid.*)

In practice, you will likely use a combination of (1) and (2). For example, you'll store the bearer token
in a config file. The file's format supports configuring *multiple* related microchains and is organized sensibly.
For example, if the ledgers live in the same database (common JDBC driver settings), or if they use the same bearer token for access, then that information need not be duplicated per chain.

## Prerequisites

Before any of the tools below can do anything useful:

1. **Create an account** at the microchain website (e.g. `https://micro.crums.io`).
   This reserves your username — every chain you register lives under
   `/{user}/{chain}` (in these docs, user `bikeshop`).
2. **Create a named access token**, from your account's manage page. This token
   authorizes access to every Bearer-protected endpoint (`/commit`, `/salts`,
   `/sql-config`, `PUT /columns`) for any chain configured to use it.

The examples throughout this document use a hypothetical `bikeshop` account
with three related chains — `orders`, `order_items`, and `customers` —
backed by tables in the same on-prem SQL database.

## Command-line tools

| Tool | How to run | Best for |
|---|---|---|
| `mchain` | `mchain commit -c …` | Full CLI, aids config file setup, reads/writes chain config |
| `commit.java` | `jbang run commit.java -c …` | Commit-only script. |

For the `commit` command, both tools share the same options.  Run with `--help` for the full list.

### Command-line options 

Where feasible, options are consistent across commands. Sensitive information *ought not* be passed from the command-line (since it can be gleaned from process-info and/or shell history); instead keep sensitive
information (bearer token, passwords, etc) in a configuration file. The following lists the `commit` command's
options (`mchain commit` or `commit.java`).

```
<chain-url>              Full chain URL: https://micro.crums.io/{user}/{chain}
--token, -t <token>      Bearer access token (may be omitted when --local-config resolves it)
--local-config, -c <file>  Local JSON config file (see below)
--chain <alias>          Select a chain from --local-config's 'chains' object (see below)
--jdbc-url <url>         JDBC connection URL (overrides server config and local-config value)
--jdbc-user <user>       JDBC username
--jdbc-pass [<pass>]     JDBC password (omit value to be prompted interactively)
--jdbc-driver-jar <jar>  Path to a JDBC driver JAR to load dynamically (see below)
--timezone, --tz <tz>    IANA timezone for hashing DATE/TIMESTAMP columns
--from <n>               First row to submit (default: current chain length)
--to <n>                 Last row to submit, inclusive (mutually exclusive with --lag)
--lag <n>                Trailing rows to withhold (mutually exclusive with --to)
--batch, -b <n>          Max rows per commit request (default: 1000)
```

### Dynamic JDBC driver loading (`--jdbc-driver-jar`)

When a JDBC driver is not on the classpath, pass its JAR directly:

```sh
mchain commit https://micro.crums.io/bikeshop/orders \
    --local-config ~/.config/crums/bikechains.json \
    --jdbc-driver-jar /path/to/sqlite-jdbc-3.50.3.0.jar
```

The JAR can also be specified in the local config file with the `jdbc_driver_jar`
key (relative paths are resolved against the config file's directory):

```json
{
  "chains": {
    "orders": {
      "jdbc_url":        "jdbc:sqlite:/data/bikeshop/bikes.db",
      "jdbc_driver_jar": "drivers/sqlite-jdbc-3.50.3.0.jar",
      "by_no_query":     "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?",
      "row_count_query": "SELECT MAX(order_id) FROM orders"
    }
  }
}
```

The JAR is loaded into a JPMS named module at runtime, so it stays isolated from
the application's own module graph.

#### Native-access warnings

Some JDBC drivers bundle a native library (`.so` / `.dylib`) that they extract
and load via `System::load` at connect time.  SQLite is the most common example.
From Java 21 onwards, calling restricted methods such as `System::load` from a
named module without explicit permission prints a JVM warning to stderr:

```
WARNING: A restricted method in java.lang.System has been called
WARNING: java.lang.System::load has been called by org.sqlite.SQLiteJDBCLoader
         in module org.xerial.sqlitejdbc ...
WARNING: Use --enable-native-access=org.xerial.sqlitejdbc to avoid a warning
WARNING: Restricted methods will be blocked in a future release unless native
         access is enabled
```

The warning is about the **driver**, not about `mchain` itself — `mchain` uses
no native code of its own.

**Suppressing the warning** via `JAVA_OPTS` (the module name comes from the JAR's
`Automatic-Module-Name` manifest attribute, or `module-info.class`):

```sh
# SQLite
JAVA_OPTS="--enable-native-access=org.xerial.sqlitejdbc" mchain rows -c cfg.json -n

# Any other native driver — replace the module name accordingly
JAVA_OPTS="--enable-native-access=<module-name>" mchain commit ...
```

**Future Java compatibility:** a future JDK release will promote this warning to a
hard failure — the native library will not load at all without the flag.  If you use
a JDBC driver that bundles native code, add the appropriate `--enable-native-access`
value to your `JAVA_OPTS` now to be forward-compatible.

### Local config file (`--local-config`)

The `--local-config <file>` option reads chain configuration from a local JSON file
instead of (or in addition to) fetching it from the server.

To keep every client and collaborator working from the same definitions, chain
parameters — queries, connection details, salt scheme, column metadata — are
best maintained authoritatively **on the server**: any field a client's
`--local-config` doesn't set is fetched fresh from `/sql-config` and `/salts`
at run time. Storing a copy locally is opt-in, and mainly useful for two
reasons:

**1. Dry-run / pre-registration.**  You can configure and test the commit workflow
entirely locally — writing SQL queries, verifying the JDBC connection, and checking
that row hashes are computed correctly — before the chain exists on the server at all.
Once the results look right, register the chain on the website and start committing
for real (see [Designing and setting up a microchain](#designing-and-setting-up-a-microchain)
below for the full workflow, including moving the local definitions to the server).

**2. Keeping sensitive values out of shell history.**  Bearer tokens, salt seeds, and
JDBC connection strings passed as command-line arguments appear in shell history and
process listings.  Storing them in a file (with `chmod 600`) avoids that exposure.

#### File format

A JSON object with a top-level `chains` object holding one entry per chain,
keyed by a short local alias — each entry combines the fields from `GET
/sql-config` and `GET /salts`, plus an `access_token` field, for that chain.
A lone chain is simply a file with a single entry under `chains`; `mchain`
auto-selects it whenever the file has exactly one chain configured, so
`--chain <alias>` is only needed once a file holds more than one (see
[Multiple related chains](#multiple-related-chains) below).  All fields are
optional — absent ones are fetched from the server as normal.

**Fully configured — unsalted chain:**

```json
{
  "chains": {
    "orders": {
      "access_token":      "mcw_...",
      "by_no_query":       "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?",
      "row_count_query":   "SELECT MAX(order_id) FROM orders",
      "jdbc_url":          "jdbc:sqlite:/data/bikeshop/bikes.db",
      "jdbc_driver_jar":   "drivers/sqlite-jdbc-3.50.3.0.jar",
      "timezone":          "America/New_York",
      "default_lag":       5
    }
  }
}
```

**Fully configured — salted chain** (adds the `salts` array; the `seed` is the
32-byte secret encoded as a 43-character Base64_32 string). Customer names and
emails are more sensitive than order or line-item data, so `bikeshop` salts
this chain:

```json
{
  "chains": {
    "customers": {
      "access_token":      "mcw_...",
      "by_no_query":       "SELECT first_name, last_name, email FROM customers WHERE customer_id = ?",
      "row_count_query":   "SELECT MAX(customer_id) FROM customers",
      "jdbc_url":          "jdbc:sqlite:/data/bikeshop/bikes.db",
      "jdbc_driver_jar":   "drivers/sqlite-jdbc-3.50.3.0.jar",
      "timezone":          "America/New_York",
      "default_lag":       5,
      "salts": [
        { "seedStart": 1, "seed": "<43-char Base64_32>" }
      ]
    }
  }
}
```

A chain with multiple salt epochs has one entry per epoch, ordered by `seedStart`.
Each epoch covers rows from its `seedStart` up to (but not including) the next
epoch's `seedStart`.

Protect the file:

```sh
chmod 600 ~/.config/crums/bikechains.json
```

#### Precedence

| Priority | Source |
|---|---|
| 1 (highest) | CLI flag (`--token`, `--jdbc-url`, `--timezone`, `--lag`, …) |
| 2 | The selected chain's own field (see `--chain`) |
| 3 | The file's shared default of the same name (see below) |
| 4 | Server response (`GET /sql-config`, `GET /salts`) |

When the selected chain resolves `by_no_query` + `row_count_query`, the
`GET /sql-config` call is skipped entirely.  When it resolves a `salts`
array, `GET /salts` is skipped.

A chain's own `chain_url` field lets the `<chain-url>` CLI argument be
omitted; see `--base-chain-url` below for inferring it instead.

#### Multiple related chains

Related chains — e.g. `orders` and `order_items`, backed by tables in the same
database — often share a JDBC connection and sometimes a bearer token. Rather
than repeating those fields in every entry, set them once at the file's top
level as **shared defaults** that any chain not overriding them falls back to:

```json
{
  "base_chain_url":  "https://micro.crums.io/bikeshop",
  "jdbc_url":        "jdbc:sqlite:/data/bikeshop/bikes.db",
  "jdbc_driver_jar": "drivers/sqlite-jdbc-3.50.3.0.jar",
  "access_token":    "mcw_...",

  "chains": {
    "orders": {
      "by_no_query":     "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?",
      "row_count_query": "SELECT MAX(order_id) FROM orders"
    },
    "order_items": {
      "by_no_query":     "SELECT order_id, product_id, quantity, list_price, discount FROM order_items WHERE order_item_seq = ?",
      "row_count_query": "SELECT MAX(order_item_seq) FROM order_items"
    },
    "customers": {
      "by_no_query":     "SELECT first_name, last_name, email FROM customers WHERE customer_id = ?",
      "row_count_query": "SELECT MAX(customer_id) FROM customers",
      "salts": [
        { "seedStart": 1, "seed": "<43-char Base64_32>" }
      ]
    }
  }
}
```

A chain's own field always wins over the shared default of the same name —
here `customers` adds its own `salts` array on top of the shared connection.
A chain's `chain_url` is inferred as `base_chain_url + "/" + <alias>` when
the chain doesn't set its own — so `orders` above resolves to
`https://micro.crums.io/bikeshop/orders` for free. A `{}` entry is valid: it
means "no local overrides for this chain," everything comes from the shared
defaults, CLI flags, or the server. A chain can still override any shared
default outright — e.g. a different `chain_url` or `access_token` — by
setting its own field, useful when one related chain happens to be hosted
under a different user or token than the rest.

Build the file incrementally with `--chain <alias>` on `mchain config ...
set`:

```sh
mchain config bikechains.json set --base-chain-url https://micro.crums.io/bikeshop
mchain config bikechains.json set --jdbc-url jdbc:sqlite:/data/bikeshop/bikes.db
mchain config bikechains.json set --jdbc-driver-jar drivers/sqlite-jdbc-3.50.3.0.jar
mchain config bikechains.json set --token mcw_...
mchain config bikechains.json set --chain orders \
    --by-no-query "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?" \
    --row-count-query "SELECT MAX(order_id) FROM orders"
mchain config bikechains.json set --chain order_items \
    --by-no-query "SELECT order_id, product_id, quantity, list_price, discount FROM order_items WHERE order_item_seq = ?" \
    --row-count-query "SELECT MAX(order_item_seq) FROM order_items"
```

Every option `mchain config set` supports works the same way under `--chain`
(`--salt-seed`, `--jdbc-props`, etc.) — it's applied to that chain's entry
instead of the file's top level. Fields that are inherently per-chain
(`--chain-url`, `--by-no-query`, `--row-count-query`, `--salt-seed`,
`--salt-scheme`) require `--chain`; `--base-chain-url` always applies at the
top level, regardless of `--chain`.

With more than one chain configured, most commands need `--chain <alias>` to
say which one to operate on:

```sh
mchain status  --local-config bikechains.json --chain orders
mchain rows    --local-config bikechains.json --chain orders --row 1 --pretty
mchain commit  --local-config bikechains.json --chain orders
```

Or commit every chain in the file in one go with `mchain commit-all`:

```sh
mchain commit-all -c bikechains.json
mchain commit-all -c bikechains.json --only orders,order_items   # skip customers
mchain commit-all -c bikechains.json --lag 5                     # applied to every chain
```

`commit-all` runs the same commit logic as `mchain commit`, once per chain,
printing a `== <alias> ==` heading before each and continuing past a failed
chain rather than aborting the batch; the exit code is non-zero if any chain
failed. There's no cryptographic requirement that related chains be committed
together — each chain's commitment path is verified independently — so this
is purely an operational convenience over invoking `mchain commit` once per
chain. `mchain status` (with `--chain` omitted) similarly reports every
chain in the file when more than one is configured.

### Designing and setting up a microchain

A recommended workflow for turning an existing SQL table (or view) into a
microchain, from first query to first commit — illustrated here for the
`bikeshop` account's `orders` chain (see [Multiple related chains](#multiple-related-chains)
above for adding `order_items` and `customers` alongside it). `mchain config
<file> set <options>` creates or updates the local config file one field at a
time — options mirror the commit command flags, and any option not supplied is
left unchanged, so the file can be built up incrementally across these steps.

As noted in [Local config file](#local-config-file---local-config) above,
chain parameters ultimately belong on the server. The general shape of this
workflow, then, is: **draft and test locally, then move the authoritative
copy to the server and remove it from the local file** — steps 1–2 are the
"draft and test locally" half, steps 3–8 register everything on the server,
step 9 is the hand-off, and step 10 re-tests against what's now
server-authoritative. (Automating that hand-off — something like an
`mchain config ... push` / `pull` pair — is on the TODO list; for now, moving
the fields over is a manual step.) Steps 3–9 apply per chain — step 12 shows
what repeating them for `order_items` and `customers` leaves the local file
looking like once all three have gone through the same hand-off.

1. **Design the ledger query first.**  Before anything exists on the server,
   define the JDBC connection and the two required queries:

   ```sh
   mchain config ~/.config/crums/bikechains.json set \
       --jdbc-url jdbc:sqlite:/data/bikeshop/bikes.db \
       --jdbc-driver-jar drivers/sqlite-jdbc-3.50.3.0.jar
   mchain config ~/.config/crums/bikechains.json set --chain orders \
       --by-no-query "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?"
   mchain config ~/.config/crums/bikechains.json set --chain orders \
       --row-count-query "SELECT MAX(order_id) FROM orders"
   ```

   `by_no_query` must return **at most one row**; an empty result set is
   interpreted as a "null" row — one with zero cells, hashing to a fixed sentinel
   value (32 zeroed bytes) — rather than an error. The column values the query returns for a
   given row number must **never change** — a microchain records the
   immutable history of the query's *results*, so editing an already-hashed
   row afterward silently invalidates that row's commitment.

   This is also why `row_count_query` is typically written as
   `SELECT MAX(<id>) FROM ...` rather than `SELECT COUNT(*) FROM ...`: primary-key
   values commonly have gaps — a deleted row, a soft delete, a transaction
   that reserved an auto-increment value and then rolled back — and `MAX(id)`
   upper-bounds the *row-number range* rather than counting rows that
   currently happen to exist. Any gap in that range then surfaces as a
   legitimate, expected null row rather than a lookup failure.

   Give each selected column a deliberate name via SQL `AS`, e.g.
   `SELECT order_id, quantity AS Qty, list_price AS Price FROM order_items WHERE order_item_seq = ?`.
   `mchain rows --pretty` falls back to whatever the JDBC driver reports as
   the column's label when no name has been configured server-side (see step
   8), so a query written with clear `AS` aliases displays sensibly even
   before column metadata exists.

2. **Test the queries**, entirely offline, before registering the chain
   anywhere:

   ```sh
   mchain status -c ~/.config/crums/bikechains.json --chain orders
   mchain rows   -c ~/.config/crums/bikechains.json --chain orders --row 1 --pretty
   mchain rows   -c ~/.config/crums/bikechains.json --chain orders --where "order_id = 42" --pretty
   ```

3. **Declare the chain URL on the server** — register the chain on the
   website (see [Prerequisites](#prerequisites)), e.g. as
   `https://micro.crums.io/bikeshop/orders`.

4. **Set the chain URL** in the config file, then confirm it resolves:

   ```sh
   mchain config ~/.config/crums/bikechains.json set --chain orders \
       --chain-url https://micro.crums.io/bikeshop/orders
   mchain status -c ~/.config/crums/bikechains.json --chain orders
   ```

5. **Define the salt scheme** — preferably on the website, since the scheme
   itself is public information a verifier needs (see `GET /info` below). If
   the scheme salts any cells, the server generates a random salt seed
   automatically. That seed *is* sensitive — a chain owner who'd rather manage
   it themselves (to back it up independently, or precompute it before
   registering) can instead set the scheme and seed locally:

   ```sh
   mchain config ~/.config/crums/bikechains.json set --chain orders --salt-scheme none
   ```

  `--salt-scheme` follows the `<base>[:<except-indices>]` format (`all`, `none`, `all:0,2`, …)
  — see `mchain config set --help`. `--salt-seed` without a value generates a
   cryptographically random 32-byte seed via `SecureRandom` and prints it; it
   sets (or replaces) the single salt epoch starting at row 1. Back the seed
   up securely — it's required to reproduce any row's input hash.

6. **If the chain tracks a live system, set `default_lag`.** A
   `MAX(id)`-based row-count query reflects whatever transaction most
   recently committed — including relative to *other*, still-uncommitted
   transactions. For example: order `101`'s transaction opens first but is
   slow (or ends up rolling back); order `102`'s transaction opens afterward
   but commits first. A commit run in between would see `MAX(order_id) =
   102`, treat row `101` as available to commit, find no matching row yet,
   and permanently record it as a null row. If `101` then commits moments
   later with real data, it's too late — row `101`'s hash was already fixed
   as null. `default_lag` withholds that many trailing rows from every
   commit, giving slower or reordered transactions time to either settle or
   definitively roll back before their row number is ever captured:

   ```sh
   mchain config ~/.config/crums/bikechains.json set --chain orders --default-lag 5
   ```

   A lag of `0` (the default) is fine for a table only appended to by a
   single, short transaction at a time (e.g. a batch import); a live OLTP
   table under concurrent write load needs a lag comfortably larger than the
   longest transaction you expect to overlap with a commit run.

7. **Retrieve the chain's access token** — copy the one created in
   [Prerequisites](#prerequisites) — from its manage page on the website and
   store it, then protect the file (it now holds secrets):

   ```sh
   mchain config ~/.config/crums/bikechains.json set --token mcw_...
   chmod 600 ~/.config/crums/bikechains.json
   ```

8. **Optionally name the columns** — decorative metadata (it's never part of
   the commitment hash) that `mchain rows --pretty` displays in place of bare
   positional indices, and that future features (`/verify` receipts,
   Qute-rendered templates) will use to label cells for recipients who hold a
   source row but no bearer token. Unlike the rest of the chain's
   configuration, this is public and is set directly via the CLI — no manual
   server-side step required:

   ```sh
   mchain columns -c ~/.config/crums/bikechains.json --chain orders \
       --name 0="Customer ID" \
       --name 1="Order Date" \
       --name 2="Store ID" \
       --name 3="Staff ID"
   ```

   Options not supplied are left unchanged — the command fetches the current
   list, merges in the given `--name` / `--description` / `--clear`
   overrides, and PUTs the full merged list back. Run without any of those
   options to view the current metadata:

   ```sh
   mchain columns -c ~/.config/crums/bikechains.json --chain orders
   ```

   Column indices are 0-based, matching `--salt-scheme`. As noted in step 1,
   a query written with clear `AS` aliases already displays sensibly via the
   JDBC fallback, so this step is most useful for names the query itself
   can't express well, or for adding a longer `--description`.

9. **Move the query definitions to the server, then remove them locally.**
   Once steps 1–6 check out end-to-end against the local file, copy
   `by_no_query`, `row_count_query`, `jdbc_url`, `timezone`, and `default_lag`
   into the chain's `sql-config` on the website — doing so is what makes them
   the authoritative, shared definition (see
   [Local config file](#local-config-file---local-config) above). Then delete
   those fields from the local file — there's no `mchain config ... unset`
   yet, so this is a manual edit — leaving just enough to resolve the chain
   and its secrets:

   ```json
   {
     "base_chain_url":  "https://micro.crums.io/bikeshop",
     "access_token":    "mcw_...",
     "jdbc_url":        "jdbc:sqlite:/data/bikeshop/bikes.db",
     "jdbc_driver_jar": "drivers/sqlite-jdbc-3.50.3.0.jar",
     "chains": {
       "orders": { },
       "order_items": {
         "by_no_query":     "SELECT order_id, product_id, quantity, list_price, discount FROM order_items WHERE order_item_seq = ?",
         "row_count_query": "SELECT MAX(order_item_seq) FROM order_items"
       },
       "customers": {
         "by_no_query":     "SELECT first_name, last_name, email FROM customers WHERE customer_id = ?",
         "row_count_query": "SELECT MAX(customer_id) FROM customers"
       }
     }
   }
   ```

   (`order_items` and `customers` still carry their local queries here — only
   `orders` has been through the hand-off so far; see step 12.)

10. **Re-test**, now against the server-side configuration, to confirm
    nothing was lost in the hand-off (salt scheme, token, and column names
    all still resolve correctly end-to-end):

    ```sh
    mchain rows -c ~/.config/crums/bikechains.json --chain orders --row 1 --pretty
    ```

11. **Commit** — a few rows first as a sanity check, then everything:

    ```sh
    mchain commit -c ~/.config/crums/bikechains.json --chain orders --to 10
    mchain commit -c ~/.config/crums/bikechains.json --chain orders
    ```

12. **Repeat steps 3–9 for `order_items` and `customers`.** Once every
    related chain has been through the same hand-off, the local file holds
    nothing but shared connection details and secrets — everything per-chain
    now comes from the server:

    ```json
    {
      "base_chain_url":  "https://micro.crums.io/bikeshop",
      "access_token":    "mcw_...",
      "jdbc_url":        "jdbc:sqlite:/data/bikeshop/bikes.db",
      "jdbc_driver_jar": "drivers/sqlite-jdbc-3.50.3.0.jar",
      "chains": {
        "orders": { },
        "order_items": { },
        "customers": { }
      }
    }
    ```

13. **From here on, commit every chain in one command** with `mchain
    commit-all`, rather than running `mchain commit` once per chain — see
    [Multiple related chains](#multiple-related-chains) above for the
    `--only` / `--lag` variants:

    ```sh
    mchain commit-all -c ~/.config/crums/bikechains.json
    ```

    `commit.java` has no `commit-all` equivalent — it's a single-chain script,
    mirroring `mchain commit` rather than `mchain commit-all`. Loop over the
    aliases instead:

    ```sh
    for chain in orders order_items customers; do
        jbang run commit.java --local-config bikechains.json --chain "$chain"
    done
    ```

### Commit examples

```sh
# No chain config on the server — all config from a local file
mchain commit --local-config ~/.config/crums/bikechains.json --chain orders

# JBang equivalent:
jbang run --deps org.xerial:sqlite-jdbc:3.50.3.0 commit.java \
    --local-config ~/.config/crums/bikechains.json --chain orders

# Override the JDBC URL at run time (e.g. to test against a staging DB):
mchain commit https://micro.crums.io/bikeshop/orders \
    --local-config ~/.config/crums/bikechains.json \
    --chain orders \
    --jdbc-url jdbc:sqlite:/data/staging/bikes.db
```

## REST API reference

All chain endpoints are namespaced under `/{user}/{chain}/`.  In the examples
below, replace `https://micro.crums.io/bikeshop/orders` with your chain URL and
`$TOKEN` with the Bearer token shown on the chain's manage page.

### Endpoint summary

| Verb | Path | Auth | Description |
|---|---|---|---|
| GET | `/{user}/_chains` | — | List all chains for a user |
| GET | `/{user}/{chain}/info` | — | Chain metadata: ledger type, title, salt scheme |
| GET | `/{user}/{chain}/columns` | — | Decorative column names/descriptions |
| PUT | `/{user}/{chain}/columns` | Bearer | Replace column names/descriptions |
| GET | `/{user}/{chain}/state` | — | Skipledger commitment path (PathPack) |
| GET | `/{user}/{chain}/salts` | Bearer | Salt epoch seeds (owner only) |
| GET | `/{user}/{chain}/sql-config` | Bearer | JDBC queries, connection URL, timezone, default lag |
| POST | `/{user}/{chain}/commit` | Bearer | Append row hashes; receive updated row count |

### `GET /{user}/_chains` — list chains (public)

```sh
curl https://micro.crums.io/bikeshop/_chains
```

Returns a JSON array of chain summaries for the user.  Each entry has:
`name`, `title`, `description`, `ledger_type` (1 = SQL ledger),
`has_salt` (boolean), `created_at` (ISO-8601 timestamp).

---

### `GET /info` — chain metadata (public)

```sh
curl https://micro.crums.io/bikeshop/orders/info
```

Response fields:

| Field | Type | Description |
|---|---|---|
| `ledger_type` | int | `1` = SQL-backed ledger |
| `title` | string | Display title (omitted if not set) |
| `description` | string | (omitted if not set) |
| `salted` | boolean | Whether every cell in a row is salted; `false` means no cells are |

There is no per-column salting: a chain's rows are either entirely salted or
entirely unsalted.

### `GET` / `PUT /columns` — column metadata (public read, Bearer write)

Decorative per-column metadata: a human-readable name and optional
description, keyed by 0-based column index (matching
`SourceRow.cells()` ordering). Unlike `/sql-config`, `GET` requires no
token — this data is meant to label cells for recipients who hold a source
row but no bearer token (e.g. future `/verify` receipts, Qute-rendered
templates).

```sh
# View (public)
curl https://micro.crums.io/bikeshop/orders/columns

# Replace (Bearer; full-list replace — see `mchain columns` below for
# incremental edits that preserve entries you don't mention)
curl -X PUT \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '[
       { "index": 0, "name": "Customer ID" },
       { "index": 1, "name": "Order Date", "description": "Date the order was placed" }
     ]' \
     https://micro.crums.io/bikeshop/orders/columns
```

**Response** — a JSON array, ordered by `index` ascending:

```json
[
  { "index": 0, "name": "Customer ID" },
  { "index": 1, "name": "Order Date", "description": "Date the order was placed" }
]
```

| Field | Description |
|---|---|
| `index` | 0-based column position |
| `name` | Human-readable column name |
| `description` | Optional longer explanation (omitted if not set) |

`PUT` is a full-list replace: indices not included in the request body are
removed. Gaps in indices are allowed — not every column needs a name.

**Error responses:**

| HTTP | Condition |
|---|---|
| 401 | Missing or invalid Bearer token (`PUT` only) |
| 404 | Chain not found |
| 422 | Malformed body, blank `name`, negative `index`, or duplicate `index` |

### `GET /state` — commitment path (public)

Returns a skipledger **PathPack**: a compact hash proof linking one or more
rows to the chain's latest committed state.

```sh
# Default: path from row 1 to the latest committed row
curl "https://micro.crums.io/bikeshop/orders/state"

# Singleton path for the latest row (used by mchain status / commit workflow)
curl "https://micro.crums.io/bikeshop/orders/state?rows=last"

# Path linking rows 5, 11, and the latest; hex-encoded hashes
curl "https://micro.crums.io/bikeshop/orders/state?rows=5,11,last&enc=hex"
```

#### Query parameters

| Parameter  | Default  | Description |
|------------|----------|-------------|
| `rows`     | `1,last` | Comma-separated stitch row numbers (1-based) and/or `last` (the latest committed row). At least one token is required. |
| `enc`      | `b64`    | Hash encoding: `b64` (43-char Base64_32, URL-safe) or `hex` (64-char hex) |
| `compress` | `1`      | `1` to return a compressed path (if compressible); `0` for a full path |

#### Stitch-row expansion

The `rows` values are *stitch row numbers*.  Connecting any two rows in a
skipledger requires passing through a specific set of intermediate rows
determined by the skipledger skip structure.  The server expands the
requested set to include all required intermediaries automatically.

Examples:

| `rows=` | Expanded stitch rows |
|---|---|
| `last` | `[N]` (singleton) |
| `1,last` | `[1, 2, 4, 8, …, N]` (full ladder) |
| `1,16` | `[1, 2, 4, 8, 16]` |
| `3,31` | `[3, 4, 8, 16, 24, 28, 30, 31]` |

The expansion rules are defined by `SkipLedger.stitch()` / `stitchCompress()`
in the `skipledger-base` module.

#### PathPack response

Skipledger commitment paths (succinct hash proof linkings the commitment hashes of
any number of rows in the ledger together) are encoded as `PathPack`s. A path-pack
contains very little redundant data. For example, the commitment hash of the
last row in a path-pack is *not written*; only its *input hash* is: the commitment
hash of the row is *computed* by the client.

```json
{
  "stitch_rows": [1, 16],
  "compression": 1,
  "hashes":      ["<hash>", "<hash>", "<hash>", "<hash>", "<hash>", "…"]
}
```

`stitch_rows` lists the row numbers that must be included in the path. As noted
above, stitch-row numbers `[1, 16]` expands to `[1, 2, 4, 8, 16]` (and are
equivalent); the server, however, always chooses the most compact (abbreviated)
representation (`[1, 16]` in the example above). For each row number (after
expansion), the response returns its **input hash** — the SHA-256 of the source
ledger row — along with whatever auxiliary hashes are needed for a verifier to
derive each row's skipledger commitment hash.  Commitment hashes are not
transmitted directly; they are computed from the input hashes and auxiliary
hashes by the verifying client.

Paths, and hence path-packs, are sticky: any 2 path-packs whose commitment hashes conflict at
an overlapping row-number do not belong to the same chain; conversely, whenever their commitment hashes
match at some row-number, the 2 paths belong to the same chain *up to* that row number.
Under the right conditions, 2 paths can be independently concatenated. When `compress=0`,
roughly (log *N*)<sup>2</sup> row hashes are present in the path (where *N* is difference
of highest and lowest row-number in the path); when `compress=1`, only roughly log *N*
row hashes are present. So `compress=0` is more sticky than `compress=1`.

#### Error responses

| HTTP | Condition |
|---|---|
| 404 | Chain not found, or chain has no committed rows |
| 422 | `rows` contains an invalid token or a row number < 1 |

### `GET /salts` — salt epochs (Bearer)

```sh
curl -H "Authorization: Bearer $TOKEN" \
     https://micro.crums.io/bikeshop/orders/salts
```

Returns an array of salt epoch objects, ordered by `seed_start` ascending.
Each epoch covers rows from its `seed_start` up to (but not including) the
next epoch's `seed_start`, or indefinitely if it is the last epoch.

```json
[
  { "seed_start": 1,    "seed": "<43-char Base64_32>" },
  { "seed_start": 5001, "seed": "<43-char Base64_32>" }
]
```

The `seed` is the 256-bit secret used to derive per-cell salts for all rows
in that epoch.  It is required to reproduce the input hash of any revealed
row; keep it confidential.

---

### `GET /sql-config` — JDBC configuration (Bearer)

```sh
curl -H "Authorization: Bearer $TOKEN" \
     https://micro.crums.io/bikeshop/orders/sql-config
```

Returns the SQL ledger configuration stored server-side.  All fields except
`by_no_query` and `row_count_query` are optional and omitted when not set.

```json
{
  "by_no_query":       "SELECT customer_id, order_date, store_id, staff_id FROM orders WHERE order_id = ?",
  "row_count_query":   "SELECT MAX(order_id) FROM orders",
  "jdbc_url":          "jdbc:sqlite:/data/bikeshop/bikes.db",
  "jdbc_driver_class": "org.sqlite.JDBC",
  "timezone":          "America/New_York",
  "default_lag":       5
}
```

| Field | Description |
|---|---|
| `by_no_query` | Parameterised SQL returning at most one row by its 1-based row number (single `?`) |
| `row_count_query` | No-parameter SQL returning the current row count as a single integer |
| `jdbc_url` | JDBC connection URL; overridden by `--jdbc-url` on the CLI |
| `jdbc_driver_class` | Fully-qualified JDBC driver class (optional; usually auto-detected) |
| `timezone` | IANA timezone for hashing `DATE`/`TIMESTAMP` columns (e.g. `America/New_York`). Defaults to UTC when absent. Must match the timezone used when existing chain hashes were built. |
| `default_lag` | Default number of trailing source rows to withhold from each commit, guarding against in-flight transactions whose sequence IDs appear in `MAX()` before the inserting transaction commits. Overridden by `--lag` on the CLI. |

### `POST /commit` — append row hashes (Bearer)

Hashes rows locally (via `mchain commit` or `commit.java`) and posts them to
the chain.  The endpoint is idempotent: re-submitting already-committed rows
is accepted as long as the hashes match, which is useful for overlap-based
sanity checks.

```sh
curl -X POST \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "start_row": 42,
       "input_hashes": [
         "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
         "BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB"
       ]
     }' \
     https://micro.crums.io/bikeshop/orders/commit
```

`start_row` must be ≤ the number of already-committed rows + 1.  Each hash
in `input_hashes` is a 43-character Base64_32 (URL-safe) encoding of the
32-byte SHA-256 input hash for that row.

**Success (HTTP 200):**
```json
{ "row_count": 43 }
```

**Error responses:**

| HTTP | Condition |
|---|---|
| 400 | Malformed JSON |
| 401 | Missing or invalid Bearer token |
| 404 | Chain not found |
| 409 | A submitted hash conflicts with an already-recorded row hash |
| 422 | `start_row` < 1, `input_hashes` empty, or a hash value is malformed |

### Native installer (`jpackage`)

`mchain` loads JDBC drivers dynamically at run time (see
[`--jdbc-driver-jar`](#dynamic-jdbc-driver-loading---jdbc-driver-jar) above), so it can't be
compiled ahead-of-time (e.g. GraalVM native-image). Instead, a self-contained
installer bundling a Java runtime is built with `jpackage`, using the
`@file`-style option files under `jpckg/` (shared attribution/icon) and
`microchain-cli/jpckg/base` (module name, description).

`jpackage` can't cross-compile: each installer must be built on its target OS,
from the `microchain-cli` subdirectory after `mvn package`:

```
# Linux — produces a .deb or .rpm, depending on distro
$ jpackage @jpckg/base @../jpckg/attrib @../jpckg/linux

# macOS
$ jpackage @jpckg/base @../jpckg/attrib @../jpckg/mac

# Windows — @..\jpckg\file doesn't work; copy the shared files in first
> copy ..\jpckg\attrib jpckg
> copy ..\jpckg\win jpckg
> copy ..\jpckg\logo.ico jpckg
> jpackage @jpckg\base @jpckg\attrib @jpckg\win
```

The `.github/workflows/release.yml` workflow automates this across all three
OSes (via a build matrix) and attaches the resulting installers to a GitHub
Release whenever a `v*` tag is pushed. It also checks out and installs
`skipledger`, `io-util`, and `merkle-tree` from source first, since those are
still SNAPSHOT dependencies not published anywhere CI can otherwise resolve
them from.
